# 需求：crypto-futures —— 合约持仓结构监控与告警

> 状态：**需求已评审通过，M1 已实现（2026-11-17）**；实现与本文的差异见 [design.md](design.md) §1（只用已收盘周期）、§4（「同轮合并」按同一数据点）、§7（健康告警冷却沿用仓库统一的 60 分钟）；2026-11-17 按 PR #39 评审意见修订（5m 口径重新回测、冷启动、历史参照、过期与健康检查）｜模块目录：`crypto-futures/`（实现时用 `make new-module` 生成；该命令不会覆盖本文件）
> 关联：[crypto-price 需求](../crypto-price/requirement.md) · [消息发送规范](../notify-policy.md) · [约定](../conventions.md)
> 命名：交易所把这块业务叫「合约 / Futures」（Binance `fapi`、OKX Futures/Perpetual）；不用 `contract`（容易被理解成智能合约），也不用 `derivatives`（还包括期权，超出关注范围）。

## 1. 要解决什么问题（一句话）

盯住 **BTC / ETH / BNB** 永续合约的**持仓结构**：多少账户偏多、大户的多空持仓怎么变、主动买卖是否失衡、杠杆是否往一边拥挤。
出现「账户比与大户持仓比背离」「账户比急转」「主动买卖严重失衡」「单边拥挤叠加加杠杆」时通过 Telegram 推送，
并说清楚**这说明了什么、不说明什么**。

目前仓库只有资金费率和 OI 两个合约指标（在 crypto-price 里），看不到多空比。现有两个相近指标都不是多空比：

| 现有指标 | 位置 | 为什么不够 |
|---|---|---|
| `taker_5m.sell_ratio` | crypto-onchain | Binance **现货**逐笔主动卖出占比，是成交流量，不是持仓 |
| `liq_15m.long_ratio` | crypto-onchain | **OKX** 已爆仓金额里多头的占比，只是事后结果 |

## 2. 边界：做什么 / 不做什么

### 做

1. **新建独立模块 `crypto-futures`**：每 300 秒一轮，与 crypto-price 的 P0 价格告警链路完全隔离。
2. **采集**（Binance USD-M 公开接口，免 key，详见 §4）：账户多空比、大户持仓多空比、合约主动买卖量比、OI 历史、资金费率。资金费率和 OI 由本模块自己采集，不依赖 crypto-price。
3. **线上粒度 = 5m**：采集、规则评估、回测、回放全部用 5m 点；所有「N 小时前」都按**时间戳精确对齐**取那一个点（取不到就视为缺失，不找近似点）。
4. **本地历史**：自采 5m 序列保留 **7 天**；冷启动与缺口回补见 §3.3。另存「触发记录」（每条约 200 字节，保留 365 天）供历史参照（§3.4）。
5. **告警规则**（§3）：本期就推送，按 [notify-policy](../notify-policy.md) 属**即时类**，全天即时、无静默。
6. **新告警卡片**（§5）：结论先行、数字带对比、写清口径和局限、附历史参照；作为本仓库合约类告警的标准样式。
7. **导出**：`data/exports/latest.json`（新契约 `futures/snapshot/v1`），供其他模块以后只读消费。
8. **回测脚本** `scripts/backtest.py`：与线上**共用同一份规则代码**，输入近 30 天 5m 数据，输出各规则触发次数与推送量；离线可重跑。
9. 离线可测：`--fixtures`、`--dry-run` 不联网；测试与回放**绝不**真发 Telegram。

### 不做

- 不接 OKX / Bybit 等其他所的多空比（本期只做 Binance 单所，所有卡片和导出都标注「Binance USD-M 单所」）；
- 不接 CoinGlass 等付费聚合源；不回补超过 30 天的历史（接口不提供）；
- **不预测涨跌、不给买卖建议**：卡片只描述持仓结构，历史参照如实给出涨跌各几次；
- 不采集大户**账户**多空比（`topLongShortAccountRatio`，与另外两项信息重叠）；
- 不改 crypto-onchain、crypto-analyst（日报展示、归因接入都放 M3）；
- 本期不搬 crypto-price 的资金费率 / OI 告警（见 §8 M2）。

## 3. 触发条件与等级

### 3.1 规则

记号：`G` = 账户多空比，`T` = 大户持仓多空比，`chg(X, Δ)` = X 当前点相对**恰好 Δ 之前那个点**的变化百分比。
阈值全部写在 `config/rules.yaml`；下表数字来自 5m 线上口径回测（§9）。

| 规则 | 中文名 | 条件 | 级别 | 方向（冷却键的一部分） |
|---|---|---|---|---|
| `crowding_build` | 拥挤加杠杆 | `chg(OI 美元价值, 4h) ≥ +5%`，且 `G` ≥ 过去 7 天 p95 或 ≤ p5 | **P0** | `long`（≥p95）/ `short`（≤p5） |
| `smart_divergence` | 账户比与大户持仓比背离 | `chg(G, 24h) ≥ +15%` 且 `chg(T, 24h) ≤ −15%`，或两者方向相反 | P1 | `retail_long` / `retail_short` |
| `retail_shift` | 账户比急转 | `abs(chg(G, 1h)) ≥ 20%` | P1 | `up` / `down` |
| `taker_burst` | 合约主动买卖失衡 | 最近 3 个 5m 点：`R = Σ买入量 / Σ卖出量`（先分别求和再相除，不对比值取平均），`R ≥ 3.5` 或 `R ≤ 1/3.5`；且 `Σ(买入量+卖出量)` ≥ 过去 24h 同口径 15m 成交量中位数的 3 倍 | P1 | `buy` / `sell` |
| `extreme_level` | 账户比创 7 天极值 | `G` 高于过去 7 天最高或低于最低 | P2（只落盘，不推送） | `high` / `low` |

- 「过去 7 天」= 当前点之前的 2016 个 5m 点，**不含当前点**；有效点数不足 90% 时该规则不评估（记日志，不告警）。
- 某条规则用到的任一输入缺失或过期（§3.3），只跳过这条规则，其余规则照常评估。

### 3.2 治理

- **冷却**：同规则 + 同资产 + 同方向。默认 **4 小时**；`smart_divergence` 用 **12 小时**（24h 窗口的条件会持续成立，4 小时会反复报）。
- **加剧**：冷却期内幅度达到上次推送的 **1.5 倍**，且距上次推送 **≥1 小时**，可再推一次，卡片标注「加剧」。
- **同轮合并**：同一资产同一轮命中多条规则只发一张卡，级别最高的作标题，其余列在「同时出现」。
- **P0 上限**：每资产每天最多 2 条，「天」按系统本地时区切分（与仓库其他模块一致）。
- **跨模块**：触发时常伴随价格大波动，可能在全仓预算的 30 分钟相关窗口里被判为「跨模块重复」。预算目前是 `observe` 模式不拦截；11-23 评审是否切 `enforce` 时把本模块纳入统计（台账 `kind=signal`）。

### 3.3 采集、过期与冷启动

- **每轮取最近 12 个点**（`limit=12`，覆盖 1 小时），按 `timestamp` 去重后并入本地历史，避免接口延迟抖动导致漏点；
- **缺口回补**：发现本地历史有 > 1 小时的缺口（Mac 休眠等），用 `startTime/endTime` 分页回补，单次 `limit ≤ 500`；
- **冷启动**：首次运行或本地历史不足 7 天时，先从接口回补最近 7 天（每资产每接口约 5 次请求）再评估。所以上线当天所有规则就可用，不存在「首周 P0 失效」；
- **过期按接口判断**：某接口最新点距当前 **> 20 分钟**（实测最大延迟约 12 分钟，留 8 分钟余量）即为过期，只影响用到它的规则；
- **30 天缓存**：每天重拉一次近 30 天 5m 数据，`startTime` 取「当前 − 29.5 天」（留出时钟偏差余量；已实测可用），万一返回 `-1130` 改用 29 天重试一次；只用于历史参照（§3.4），覆盖写、不累积。

### 3.4 历史参照（卡片里的一行）

- **统计范围**：**同一规则、3 个资产合并**，触发时间早于当前且**已满 24 小时**的历史触发（排除当前这次，也排除结果还没出来的）；
- **数据来源**：本地触发记录（上线后累积）+ 上线前用 30 天缓存按同一规则代码回放出的触发（只做一次预热）；
- **展示**：「近 N 天同规则（3 币）M 次，之后 24h 涨 a 次 / 跌 b 次，中位数 x%」；**M < 3 时只显示「样本不足（M 次）」**；
- 这一行提醒「这类信号历史上不总是对的」，不是预测。按回测频率，上线头几周大多会显示「样本不足」，这是预期行为。

## 4. 数据源 / 输入

全部为 Binance USD-M 公开接口，2026-11-17 已联网核实（BTC/ETH/BNB 均 HTTP 200）。

| 指标 | 接口 | 含义 | 每轮请求 |
|---|---|---|---|
| 账户多空比 `G` | `/futures/data/globalLongShortAccountRatio` | 净持多仓的**账户数** / 净持空仓的账户数（只数账户，不看仓位大小） | 1 次，`period=5m&limit=12` |
| 大户持仓多空比 `T` | `/futures/data/topLongShortPositionRatio` | 保证金前 20% 用户的多仓**持仓量** / 空仓持仓量 | 同上 |
| 合约主动买卖量比 | `/futures/data/takerlongshortRatio` | 合约 taker 买入量 / 卖出量（带 `buyVol`/`sellVol`） | 同上 |
| OI 历史 | `/futures/data/openInterestHist` | 全市场持仓量（张数 `sumOpenInterest` + 美元价值 `sumOpenInterestValue`） | 同上 |
| 资金费率 | `/fapi/v1/premiumIndex` | 当前周期资金费率 `lastFundingRate`、标记价（实时快照，无历史 `timestamp`） | 1 次 |

已核实的事实：

- 只能查最近 30 天（超过报 `-1130`；29.5 天可用）；单次 `limit` ≤ 500；
- 数据延迟各接口不同：实测最新点距当前约 100s / 400s / 700s（大户持仓 / 账户 / 主动买卖）；
- 请求量：常规每轮 3 资产 × 5 接口 = **15 次 / 5 分钟**；每日 30 天缓存约 3 × 4 × 18 = **216 次**（一次性、限速排队）；
- **合约价** = `sumOpenInterestValue / sumOpenInterest`；`sumOpenInterest` 为 0 或缺失时合约价记为 `None`，卡片显示「—」，依赖价格的历史参照跳过该点。

## 5. 告警卡片

### 5.1 现有卡片的问题（crypto-price 的资金费率 / OI 告警）

1. 标题统一写「价格异动」，资金费率告警也这么写，看标题不知道是什么事；
2. 标题句和明细重复同一串数字，真正的结论反而不突出；
3. 衍生品告警也显示「多源核验 3/3」，但资金费率 / OI 其实只有 Binance 单源，会误导；
4. 只有单个指标，看不到背景（资金费率告警看不到 OI，更没有多空比）；
5. 没有说明「这不代表什么」，也没有历史参照，容易被当成买卖信号。

### 5.2 新卡片规范

| 区块 | 内容 | 要求 |
|---|---|---|
| 标题 | `图标【crypto-futures】级别 · 资产 规则中文名` | 必有 |
| 结论 | 一句白话（加粗） | 必有；只描述指标本身的变化 |
| 指标 | 触发规则用到的指标，每项一行：当前值（对比值，变化）· 占比 / 7 天位置 | 必有；不用表格（Telegram 等宽字体下中文对不齐） |
| 背景 | **固定三项、固定顺序**：合约价（24h 涨跌）· OI 美元价值（4h 变化）· 资金费率 | 必有；某项缺失显示「—」 |
| 同时出现 | 同轮命中的其他规则 | 没有就不显示 |
| 解读 | 1–2 句：说明了什么、**不说明什么** | 必有；不推断「谁在开多 / 抄底 / 减仓」，不给操作建议 |
| 历史参照 | §3.4 | 必有 |
| 口径 | `Binance USD-M 单所 · 5m 数据 · 截至 HH:MM` | 必有 |
| 页脚 | 时间 · 交易数据链接 · `🏷 任务：<Label>` · 免责 | 必有，按 notify-policy §5 |

用词约束（指标能说明的范围）：
- `G` 只数账户，写「做多的**账户**占比上升」，不写「散户在开多 / 抄底」；
- `T` 下降可能是减多也可能是加空，写「大户多空持仓比下降」，不写「大户在减仓」。

长度 ≤ 600 字；HTML 转义、超长截断复用 crypto-price 已有做法（实现时抽到 `crypto_core.notify`）。

## 6. 验收标准（可测量）

1. `make gate` 全绿；新模块单测至少覆盖：
   - 5 类响应解析：正常 / 空数组 / 字段缺失 / 非 JSON；`sumOpenInterest` 为 0 或缺失时合约价为 `None`；
   - 派生量：按时间戳精确取「N 小时前」的点，取不到返回 `None`；7 天分位数不含当前点；有效点不足 90% 不评估；
   - 5m→15m 聚合：先分别求和再相除（构造「对比值取平均会得出不同结论」的用例）；
   - 5 条规则的触发与不触发边界；`R ≤ 1/3.5` 与 `R ≥ 3.5` 对称；
   - 冷却（含 `smart_divergence` 12h）、加剧（1.5 倍且 ≥1h）、同轮合并一张卡、P0 每资产每本地日 ≤2；
   - `extreme_level` 只落盘不推送；
   - 过期按接口生效：taker 过期时其他规则照常评估；
   - 冷启动：本地历史为空时先回补 7 天再评估；回补遇到 `-1130` 时以 29 天重试；
   - 历史参照：排除当前触发和未满 24h 的触发；M < 3 显示「样本不足」。
2. 回放一致：用 §9 的 5m 数据切片做 fixtures，`--fixtures` 回放的触发记录与 `backtest.py` 在同一份数据上的输出**完全一致**（两者共用规则代码）。
3. 卡片：§5.3 三个时点的 fixtures 渲染结果包含 §5.2 的全部必有区块、背景三项顺序固定、长度 ≤ 600 字；单测断言不出现「多源核验」「开多」「抄底」「减仓」字样。
4. `python3 scripts/run.py --once --dry-run --json` 联网输出 3 资产 × 5 指标：四个 `/futures/data` 指标与同一 `timestamp` 的接口返回完全一致；资金费率与同一分钟内单独请求 `premiumIndex` 得到的 `lastFundingRate` 一致。
5. 请求量：常规 ≤ 15 次 / 5 分钟（M2 起 ≤ 18 次，见 [requirement-m2.md](requirement-m2.md) §4.5）；每日 30 天缓存 ≤ 220 次；单次 `limit` ≤ 500。
6. 失败降级：断网或 429 时记 SKIP、rc=0、不告警。**任一接口**连续失败或过期超过 1 小时，自检发一条健康告警（按接口去重，6 小时冷却；复用现有 healthcheck），避免单条规则静默失效。
7. 上线运行 24 小时：每资产每接口本地点数 ≥ 280（理论 288），无重复点，`data/` 增长 < 5 MB/天；`collect.log` 每 300 秒有 start/done。
8. 上线首周：实际推送量与 §9 估算同量级（≤ 2 条/天）；超出则调阈值并记录。每条推送在台账里 `module=crypto-futures`、`kind=signal`。

## 9. 回测依据

- **数据**：Binance `/futures/data/*`，2026-10-18 至 11-17，**5m 粒度**（与线上一致），每资产每接口 8497 点；资金费率用 `/fapi/v1/fundingRate` 结算记录；
- **口径**：与 §3 完全一致（精确时间戳对齐、方向冷却、`smart_divergence` 12h、1.5 倍 + ≥1h 加剧、同轮合并、P0 每本地日 ≤2）；前 24 小时作预热，7 天类规则从第 8 天起评估；
- **结果**（3 币合计，可评估约 28.5 天）：

| 规则 | 触发 | 说明 |
|---|---|---|
| `crowding_build`（P0） | 2 | BNB 10-30（long）、ETH 11-04（short）；可评估约 21.5 天 |
| `smart_divergence` | 7 | |
| `retail_shift` | 4 | |
| `taker_burst` | 2 | |
| `extreme_level`（P2，不推） | 64 | 太频繁，所以只落盘 |
| **推送卡片合计** | **15（约 0.53 条/天）** | BTC 8 · BNB 4 · ETH 3；远低于全仓预算 `daily_signal_cap=10` |

- **阈值怎么来的**：最初按 15m 粒度回测定的阈值（急转 15%、背离 10%、失衡 3.0）放到 5m 线上口径下会推到约 1.8 条/天，所以收紧为 20% / 15% / 3.5，背离冷却改为 12h；
- **单项灵敏度**（其他阈值不变、冷却 4h 时的触发次数）：急转 10% 31 次 · 15% 14 · 20% 7 · 25% 5；背离 10% 24 · 12% 14 · 15% 11；失衡 3.0 倍 11 · 3.5 倍 2 · 4.0 倍 0；
- **方向不稳定**：早期 15m 回测里 7 次背离之后 24h 价格为 −0.2%、−5.2%、+0.1%、+3.9%、−2.1%、−3.0%、+1.1%，所以卡片不暗示方向；
- 本次分析脚本是一次性的，不入库；实现时按同一口径写成 `scripts/backtest.py`（验收 2）。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 被当成买卖信号 | 卡片必有「不说明什么」和历史参照；用词约束（§5.2）；回测已显示方向不稳定 |
| Binance 单所偏差 | 所有输出标注口径；M3 再考虑多所 |
| 阈值基于约 30 天样本，行情风格变了会失准 | 阈值全在配置；`backtest.py` 可随时重跑；上线首周看台账推送量 |
| 与 crypto-price 价格告警同时出现，用户觉得重复 | 内容不重叠（本模块讲持仓结构）；纳入全仓预算的跨模块统计，11-23 一起评审 |
| 接口延迟（最多约 12 分钟）、单接口长期失效 | 卡片写「截至 HH:MM」；按接口判过期（20 分钟）；单接口失败/过期超 1 小时发健康告警 |
| 接口限频 / 临时封禁 | 走 `crypto_core.http`；SKIP 不告警，下一轮重试 |
| Mac 休眠造成缺口 | 下轮按缺口分页回补；回补期间的历史触发只落盘不补推 |

## 11. 评审结论（2026-11-17）

1. §3.1 的 5 条规则通过，`crowding_build` 定为 P0；PR #39 评审后按 5m 口径重新回测，阈值收紧为 §3.1 现值（规则结构不变）；
2. §5.3 的卡片样式与内容通过，作为合约类告警的标准样式；
3. M2（迁移 crypto-price 的资金费率 / OI 告警）不并入本期，M1 上线后单独评审。
