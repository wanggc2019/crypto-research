# 会话干活与收尾规范（每轮必须执行）

目标：用户在并行开很多会话、不会逐个追问。**每个会话自己说清楚：做到哪、完成多少、还差什么、需要确认什么、做完没有。**

配套硬规则：`AGENTS.md` §9（每轮回复结尾必须带状态块），本 skill 是它的完整执行版。

## 1. 开工：先定义「完成」（5 分钟内做完）

在动手前，先给自己（和用户）写下三样东西，**第一条回复就给出**：

1. **验收项**：1–5 条可勾选的验收标准，每条都能量化验证，例如：
   - `make gate` 全绿
   - PR #N 已合并 / commit `<sha>` 在 main
   - `crypto-x/scripts/run.sh --dry-run` 输出包含 `<字段>`
   - `docs/<module>/requirement.md` 更新且验收标准可测量
2. **不做什么**：边界（避免范围膨胀，也方便判断完成）。
3. **完成度口径**：按验收项比例算（见 §4），开工报 0% 或当前值。

用 `todo_write` 或回复里的清单登记验收项，后面每轮都按它勾选。

### 开工回复模板（不要长篇，直接给要素）

```text
目标：<一句话>
验收项：1) ... 2) ... 3) ...
不做：...
预计：<步骤数/较短的路径>；需要你确认：<无 / 事项>
```

## 2. 干活中：主动汇报，不等用户问

**触发时机（每个都要报，不是等用户问）：**

- 每完成一个验收项；
- 每一轮回复的结尾（无论是否完成）；
- 遇到阻塞/需要决策/需要凭据/有风险要选方案时（**立即**报，不要自己猜着做到底）；
- 准备收尾时（先报「即将收尾 + 自验计划」）。

汇报只写变化和判断，不写流水账：

```text
进度：验收项 2/5 通过（40%）；正在做 3)
卡点：无 / <具体>
需要确认：无 / <需要决定的具体问题，必要时给 A/B 选项>
```

### 什么时候必须停下来问用户（「需要你确认」必填内容）

- 需求边界有歧义，继续做可能白做；
- 有多个方案且影响面不同（调度/凭据/外部 API/数据保留策略）；
- 需要写仓库外的东西（`~/Library/LaunchAgents`、系统配置、删除数据）；
- 涉及推送/真实告警、花钱/限额、合规灰色地带；
- 发现并行会话在做同一件事（先问「合并还是让路」，不要各做一套）。

## 3. 自验：收尾前必须自己跑，不把验证丢给用户

按任务类型选验证方式，**证据必须可复核**（贴命令/输出摘要/PR/commit/文件路径）：

| 任务类型 | 必跑 |
|---|---|
| 改代码（任一模块/libs/tools） | `make gate`（ruff + 全部单测 + 回放 E2E）；新增/修复行为先补测试 |
| 改调度/launchd | `make launchd module=<name> action=status`；`make jobs` 确认无异常 |
| 改推送/消息 | `run.sh --dry-run` 看产物；必要时 `--test`（标明测试样例）；**不要**用 `--notify` 回放旧快照 |
| 改数据源 | 离线 fixtures 优先；联网冒烟用 `python3 tools/gate.py --with-network`（外部失败只警告） |
| 纯文档 | 与代码/事实一致；命令可复制执行；中英文/路径/链接无误 |
| 取消/改方案 | 明确终止 + 回滚：`git status` 无残留、无未装完的定时任务/plist、无半成品文件 |

收尾前自检（逐条勾）：

- [ ] 验收项逐条对照，全部有证据；
- [ ] `make gate` 全绿（代码类任务）；
- [ ] `git status` 里没有本轮不该有的未提交改动（别人的 WIP 不要动）；
- [ ] 分支/PR/CI/合并按仓库规则走完（或明确写「未做，原因」）；
- [ ] 没有残留的后台任务、临时脚本、测试消息、装到一半的调度。

## 4. 完成度怎么算（不要拍脑袋）

- 以**验收项**为分母：完成度 = 已通过项数 / 总项数，四舍五入到 5%；
- 只有一个验收项时，按该事项内部阶段估（0/25/50/75/100），并在「进度」里写当前阶段；
- **100% 的定义**：全部验收项通过 + 自验全绿 + 已提交并合并（或按任务约定不需要合并）+
  没有「需要你确认」的阻塞项；
- **禁止**把「代码写完」「本轮跑完」「测试跑了一半」写成 100% 或「已完成」。

## 5. 收尾：固定报告（必须，用户不问你也要给）

```text
状态：✅ 已完成 / ⏳ 进行中 / ❌ 未完成（原因）
完成度：xx%（通过 x/y 项）
进度：做到哪一步
证据：命令结果 / commit / PR 号 / 文件路径
需要你确认：具体问题（没有就写「无」）
下一步：谁做什么
```

规则：

- 「状态」只有三种；不允许用「收尾完成」「基本完成」这类模糊词；
- 未完成必须写清 **还差什么、卡在哪、谁能推进**（用户/外部/时间）；
- 需要决策的事项，**必须单独一行**，必要时给选项：`A) … B) … 推荐 A，因为…`；
- 一轮结束但任务没完：状态写「⏳ 进行中」，不要写完成；
- 如果用户可能要离开：在「下一步」里写「你不在时我可以继续做 X，不需要你操作」。

## 6. 反例（出现即视为违规）

- ❌ 回复里只说「已处理/已完成」，没有证据和完成度；
- ❌ 把「本次回复结束」当成「任务完成」；
- ❌ 遇到歧义/需要授权就自己猜，做完才说；
- ❌ 需要确认的事埋在一大段文字里，没有单列；
- ❌ 让用户自己跑测试/自己看日志才知道结果；
- ❌ 任务被取消后留一堆未提交文件或装了一半的配置。

## 7. 与仓库流程的关系

本 skill 只管「汇报与收尾」，不替代仓库开发流程；开工检查、分支/PR/CI/合并、测试命令等仍按
`AGENTS.md`、`docs/conventions.md` 与 `crypto-research-workflow` skill 执行。
